# Mobile private-chat push notifications

Backend implementation only. The web-service polling option requires no new migration or mobile API change. No Render deployment was performed for this update; the authorized live verification below used a temporary local web app connected to Supabase and Expo.

## Mobile API contract

Use the existing application access JWT from NestJS, including for Google users. These routes require `Authorization: Bearer <accessToken>`. They do not accept a user ID or session ID from the client. An expired/revoked session or disabled account returns `401`.

Generate a random UUID once per app installation and persist it across logins and account changes. This is `deviceId`; it is not a user ID, session ID, Expo project ID, or hardware identifier.

### Register / update this installation

`PUT /api/v1/me/push-devices/:deviceId`

```http
Authorization: Bearer <application-access-token>
Content-Type: application/json
```

```json
{"expoPushToken":"ExpoPushToken[the-token-from-expo]"}
```

`ExponentPushToken[...]` is also accepted. The token is trimmed; invalid tokens, invalid UUIDs, and extra body fields return `400`. Use an Expo push token, not an APNs/FCM native token.

Response: **200**, JSON:

```json
{"deviceId":"11111111-1111-4111-8111-111111111111","registered":true}
```

Repeating an identical registration for the same signed-in session is idempotent. Each account can register multiple installations. A token and installation each have exactly one active binding. Registering either under another account/session replaces its old binding and deletes deliveries queued for that old binding. This also handles token rotation. Replaced jobs are never retargeted to the new account.

### Unregister this installation

`DELETE /api/v1/me/push-devices/:deviceId`

Same Bearer authentication. No request body. Response: **204**, empty body. Repeated calls are safe. It only removes the binding owned by the current user **and current session**, so an old account/session cannot unregister its replacement.

### Login, refresh, logout, account switching

1. Configure Expo/EAS Android/iOS push credentials and native notification permissions in the mobile project. Obtain an Expo push token for that Expo project after permission is granted. Never put `EXPO_ACCESS_TOKEN` in the app.
2. After every successful login, register the installation/token using the new Nest access token. Also register again whenever Expo reports a token change. Refreshing an access token within the same session does not remove registration.
3. Before logout or switching accounts, call `DELETE` while the old access token still exists. Then complete the existing Nest logout flow and clear local credentials and displayed notifications. If offline, retry server logout/unregistration when connectivity permits; clearing local state alone cannot notify the backend.
4. Existing `POST /api/v1/auth/logout` uses the refresh cookie and the existing allowed `Origin` header; it returns `200` with `{"message":"Logged out successfully"}`. It is not a new Bearer-only logout route. Do not invent a refresh-token JSON body. Session revocation also deletes all push registrations bound to that session, including logout, password changes/reset, refresh-token reuse, and admin revocation.
5. Register immediately with the new account/session after switching. Keep the same installation UUID. A session that expires without explicit logout is excluded at enqueue and delivery time. Other devices remain registered unless their sessions are also revoked.

## Notification contract

A saved private message produces a visible notification for **each registered recipient device**, including when the mobile app is closed. Foreground Socket.IO behavior is unchanged; pushes are not suppressed just because the user has an open socket.

Example Expo request generated by the worker:

```json
{
  "to":"ExpoPushToken[recipient-device]",
  "title":"BlogHub",
  "body":"New message from Alice",
  "sound":"default",
  "ttl":3600,
  "tag":"33333333-3333-4333-8333-333333333333",
  "collapseId":"33333333-3333-4333-8333-333333333333",
  "data":{
    "type":"chat_message",
    "conversationId":"22222222-2222-4222-8222-222222222222",
    "messageId":"33333333-3333-4333-8333-333333333333"
  }
}
```

The body is exactly `New message from <sender display name>`, using a snapshot of the name at send time. Private message text is never included in the notification or push job. The UUIDs in the example are placeholders.

On notification tap, including a cold app launch, read `data.type`, authenticate as the current account, and open `data.conversationId`. Fetch history using the existing authorized chat API. Use `messageId` to select the message if needed. If login is required, preserve the destination until login succeeds; handle `403/404` without showing another user's history. Deduplicate local notification handling by message ID and respect platform foreground presentation settings.

OS permissions, native push credentials, connectivity, and platform delivery rules still apply. A successful Expo receipt means APNs/FCM accepted the push, not proof that the phone displayed it. See [Expo's official push delivery contract](https://docs.expo.dev/push-notifications/sending-notifications/).

## Database and transaction changes

Migration: `src/database/migrations/1794441600000-AddChatPush.ts`.

- `push_devices`: immutable registration ID, installation UUID, unique Expo token, user and refresh-session foreign keys, creation time. Token and installation uniqueness prevent multiple active account bindings.
- `push_jobs`: message + registration IDs (unique pair), sender name snapshot, status, attempt counters, ticket ID, next attempt time, short error code. Message/registration deletion cascades jobs. Both tables enable RLS without public policies; use the existing private backend database role, not a public Supabase client.
- `refresh_sessions_push_cleanup`: database trigger that removes session registrations when `revoked_at` is set. It covers every existing session-revocation path without introducing auth/push service dependency cycles.

`ChatRepository.saveMessage()` inserts jobs in the same PostgreSQL transaction as a newly inserted message. Existing `clientMessageId` retries return the original message and do not create jobs again. Failed/rolled-back message transactions leave no jobs. Database transaction failures still fail the write atomically; Expo delivery errors never enter that transaction or affect the chat acknowledgement.

Only active recipient registrations are captured; sender/unrelated devices are excluded. The worker rechecks the current user, session, immutable registration, message deletion, and recipient before delivery. Revoked/switched registrations cascade queued jobs. Short parent/device locks prevent sends starting after a completed logout or account transfer. They cannot recall a notification already accepted by Expo or the device OS.

## Render rollout (manual, not performed)

1. Review the migration and database backup, then apply pending migrations once from a trusted backend environment connected to the intended database:

   ```bash
   npm run migration:run
   ```

   Do this **before** starting the updated API/worker: the chat send transaction now needs both tables. Do not rely on automatic synchronization. Restarting Nest alone does not run migrations.

2. Choose one of the deployment modes below. Both reuse the same queue and worker. No mobile API contract or new migration is needed for web-service polling.

### Existing Render web service (no separate worker service)

Keep the existing web service, build command, and web start command (`node dist/main.js`). Add to its private Render environment:

```env
EXPO_PUSH_IN_WEB=true
```

Add `EXPO_ACCESS_TOKEN` to this web service only if Expo push access security is enabled. It already has the database/TLS settings. Push processing is off in the web service unless `EXPO_PUSH_IN_WEB` is exactly lowercase `true`; `EXPO_PUSH_ENABLED` does not enable web polling. Save and redeploy after pushing this code. Starting it processes existing eligible jobs, not just new messages.

The web service registers the existing worker through `PushModule`. Nest starts its asynchronous polling after initialization; chat sends never await an Expo request. Logs show `Push worker polling enabled (EXPO_PUSH_IN_WEB)` or `Push worker disabled (EXPO_PUSH_IN_WEB)`. Shutdown hooks stop polling and wait for an in-flight batch.

**Free hosting limit:** polling pauses while the Render web service sleeps or restarts. An inbound message request wakes the service; due jobs resume once it starts. Receipt checks may also be delayed. No immediate/background delivery guarantee is possible while the service is asleep; jobs older than 24 hours expire. Do not add artificial keepalive requests. Use a continuously running service/worker when timely delivery matters.

### Separate worker alternative

3. Create a separate **Render Background Worker**, from this same repository and branch. Render workers run continuously and accept no inbound HTTP traffic; see [Render Background Workers](https://render.com/docs/background-workers). A sleeping web service cannot substitute for this worker. Check the available worker plan in your workspace before provisioning.

   Build command:

   ```bash
   npm ci --include=dev && npm run build
   ```

   Start command:

   ```bash
   npm run start:push-worker
   ```

   This runs `node dist/push-worker.main.js`. Use the same supported Node version as the API (Node 22). It needs no port or HTTP health endpoint.

4. Set worker environment variables:

   | Variable | Value |
   | --- | --- |
   | `NODE_ENV` | `production` |
   | `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD`, `DB_NAME` | Same private database as the API |
   | `DB_SSL`, `DB_SSL_CA_FILE` | Same TLS configuration/certificate available on the worker |
   | `EXPO_PUSH_ENABLED` | `true` to process jobs; otherwise polling is disabled |
   | `EXPO_ACCESS_TOKEN` | Optional **server-only** Expo access token if push access security is enabled |

   The separate worker does not need JWT, SMTP, Google, or Supabase Storage credentials. The API needs the Expo access token only when web polling is enabled and Expo push access security requires it. `.env.example` defaults both polling modes to disabled. Deploying the API without either enabled mode leaves jobs queued. Prefer enabling just one mode; existing database row locks also protect claims across processes, but external transport remains at least once.

5. Configure Expo project push credentials/access security and mobile permission/token registration. Perform a real-device acceptance test separately when authorized. None was sent as part of these backend tests.

## Worker behavior and operations

- PostgreSQL outbox; no Redis, extra queue library, or Expo SDK dependency. Polls every 5 seconds, up to 25 due jobs per pass. `FOR UPDATE SKIP LOCKED` supports safe claims across worker processes. Shutdown stops polling and waits for the current bounded request.
- Expo requests time out after 10 seconds. Jobs expire after 24 hours. Provider delivery TTL is one hour once submitted.
- Successful tickets are persisted; first receipt check is after 15 minutes. Missing receipts/network errors retry receipt lookup without resending the notification. Receipt polling is bounded to 8 checks. An explicit transient delivery failure can schedule a new send.
- Sends retry transient HTTP 429/5xx, network, and rate-limit failures up to 6 total attempts, using exponential backoff starting at 30 seconds and capped at 30 minutes. Permanent credential/payload failures become `failed` for operational investigation.
- `DeviceNotRegistered` in a ticket or receipt deletes that registration and all its queued jobs. A later mobile registration creates a fresh binding.
- States: `pending`, `receipt`, `complete`, `failed`, `cancelled`. Inspect `last_error`, counters, and `next_attempt_at` in the private database. Logs include only a job ID and short error code, never tokens, credentials, or chat text. Fix credentials before investigating/resubmitting failed jobs; restarting alone does not reset terminal failures.
- Terminal jobs are retained for diagnosis. Plan periodic deletion of old `complete`, `failed`, and `cancelled` jobs according to your retention policy; active jobs must remain. Expired registration rows can also be pruned by session age. No automatic retention deletion was added.
- Chat retry enqueue is exactly once per message/registration. External transport is **at least once**: a crash or lost response after Expo accepts a push but before ticket persistence may cause a duplicate. Message-ID tags/collapse IDs and mobile deduplication help; they are not an exactly-once guarantee.

### Verify a new message

1. Send one new message to an account with a current session-bound Expo registration.
2. Inspect `push_jobs` by `message_id` in Supabase without printing device tokens. Expect `pending` initially, then `receipt`, a nonempty `ticket_id`, and `attempts` at least one after polling.
3. An accepted ticket only confirms Expo accepted the request. The worker first checks the receipt after 15 minutes; `complete` means a successful receipt. Inspect `last_error` for failures and keep credentials/token values private.
4. If a due job stays `pending` with zero attempts, check the enabled-mode startup log, the relevant flag, database identity, and `Push worker database failure; queued jobs retained`. Database rollbacks can leave zero recorded attempts even after a request; do not manually reset/re-enqueue jobs to retry.

Live check on November 13, 2026: the user sent message `6ea1f29e-4c2c-41f8-9478-2472542c5477`. Its job `f3e3cc30-cb61-4e34-8297-0e2d22f851a9` started as `pending` with zero attempts. Initializing the updated Nest web app with web polling enabled processed it to `receipt`, one attempt, a stored Expo ticket, and no error. The older eligible queued jobs were also processed. The local test app was closed afterward; no tokens or keys were printed. Final Expo receipt/device display was not verified in this check.
